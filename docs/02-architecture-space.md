# 02 — 微架构方案空间与选型（Phase 2）

> 本文档列出可行微架构方案、比较维度、以及**选定方案与工程理由**。
> 选型遵循优先级：ISA 正确性 > RTL 正确性 > 可验证性 > 结构清晰 > 可实现性 > 性能 > 面积 > 功耗。

---

## 1. 候选方案

### A. 单周期（Single-Cycle）
每条指令一拍完成：取指 → 译码 → 寄存器读 → ALU → 访存 → 写回。
- 控制：纯组合译码，**无任何冒险逻辑**（无前递、无停顿、无冲刷）。
- 关键路径：`PC → I-Mem → 译码 → RegFile → ALU → D-Mem → 写回 Mux`（且 I-Mem/D-Mem 都必须组合读）。

### B. 多周期（Multi-Cycle FSM）
一条指令分 3–5 个状态执行（如 FETCH / DECODE / EXEC / MEM / WB），单套存储器端口。
- 控制：状态机 + 状态相关的多路选择；每条指令的节拍数由状态序列决定。
- 关键路径：每个状态内部只有一段组合逻辑（例如只有 ALU，或只有存储器）。

### C. 三级流水线
`IF | ID+EX | MEM+WB`（或 `IF+ID | EX | MEM+WB`）。
- 冒险：结构冒险需处理（取指与访存争用存储器），load-use 可用 1 次停顿解决；
  分支在 EX 解析，冲刷 1–2 条。

### D. 经典五级流水线（IF / ID / EX / MEM / WB）
- 冒险：需要完整前递网络 + load-use 互锁 + 分支冲刷。
- 关键路径：每级都很短（IF：PC 选择 + 存储器读；EX：前递 Mux + ALU + 分支比较）。

### E. 加强型（≥5 级 + 动态分支预测 / 乱序 / Cache / 多发射）
- 直接违背「不要求 Cache / 不要求分支预测 / 不要求乱序 / 不引入不必要复杂度」。

---

## 2. 比较

| 维度 | A 单周期 | B 多周期 | C 三级 | **D 五级（选定）** | E 加强型 |
|---|---|---|---|---|---|
| 冒险逻辑 | 无 | 无 | 中 | 中（前递+互锁+冲刷） | 高 |
| 控制复杂度 | 最低 | 中（状态机 + 状态相关 Mux） | 中 | 中（译码 + 冒险单元） | 很高 |
| 关键路径 | **最长**（存储器×2 + ALU + RF 串在一拍） | 短（分拍） | 较长（ID+EX 合并） | 短（分级均匀） | 短 |
| 估计可达频率（FPGA） | ~40–60 MHz | ≥150 MHz | ~100 MHz | ~100–150 MHz | ≥200 MHz |
| CPI（典型整数代码） | 1.00 | 3–5 | ~1.3 | ~1.2–1.5 | <1 |
| 存储器端口需求 | 2 个组合读端口 | 1 个共享端口 | 2 个（IF/MEM 争用） | 2 个组合读端口 | 多端口/Cache |
| 结构清晰度 | 数据通路清晰、无时序交织 | **状态交织**：同一条数据通路在不同节拍承担不同角色，读代码需脑内展开状态机 | 中 | **最好**：一条指令一级，数据流单向、无反馈 | 差（评分/重命名/ROB） |
| 可验证性 | 无冒险，最易 | 需覆盖状态序列、多拍访存与分支时序 | 中 | 冒险种类多，但**每种冒险都是有限可枚举的确定条件**，可系统化枚举验证（见 `06`） | 状态空间爆炸 |
| 面积 | 最小 | 小 | 中 | 中（多 ~700 FF + 前递 Mux） | 大 |
| ISA 正确性风险 | 低 | 低，但「多拍指令中途被假设打断」类 bug 隐蔽 | 中 | 低（陷阩点唯一、精确提交点唯一） | 高 |
| 与需求符合度 | 不满足原始「五级流水线」目标 | 满足「简单」但放弃流水线 | 部分满足 | **完全满足** | 明确超出需求 |

## 3. 关键分析

### 3.1 为什么作者不选单周期
单周期确实把「冒险」这一整类 bug 从设计里删掉了，这是它对正确性的最大优势。但它有两个
与本项目需求直接冲突的点：

1. **时序**：两个组合读存储器 + ALU + 译码器在一拍内串联。即便按「不要求高主频」放宽，
   单周期在 FPGA 上通常只能跑到 40–60 MHz，且关键路径随存储器容量增长而恶化——
   这意味着「换更大的测试程序」会直接压低频率，工程上不稳健。
2. **存储器端口**：单周期要求 I/D 两个组合读端口，实际上比五级流水线更苛刻，
   并没有因为「结构简单」而降低对存储器的要求。

收益（省掉冒险逻辑）无法抵消它在时序稳健性与接口要求上的代价，故不选。

### 3.2 为什么作者不选多周期
多周期在「不追求性能」的前提下确实是复杂度很低的方案，且频率高、面积小。不选它的理由
是**可验证性**（本项目第 3 优先级）而非性能：

- 多周期的控制复杂性并不低，只是从「数据通路」转移到了「状态机」：每条指令都需要一条
  正确且互斥的状态序列，且访存/分支必须与状态对齐。这类 bug（例如 SW 在第 3 拍才写内存，
  但第 2 拍的地址寄存被下一指令提前覆盖）在波形上比流水线冒险更难定位。
- 五级流水线的冒险是**局部、可枚举、条件明确**的：前递命中条件、load-use 条件、冲刷范围，
  一共只有 3 张有限真值表（见 `03` §6）。验证可以按表逐条打勾，且能用**差分随机测试**
  自动覆盖（见 `06`）。多周期的状态序列则没有这种「一张表覆盖全部」的性质。
- 本项目的原始目标是「五级流水线 CPU」；后续澄清是**解除性能压力**（不做 Cache/预测/乱序/
  功耗优化），并非要求放弃流水线。五级顺序单发射流水线不属于「不必要的复杂机制」。

### 3.3 为什么不是三级或六级
- 三级：`ID+EX` 合并使译码 + 寄存器读 + 前递 + ALU + 分支比较挤在一级，关键路径比五级更长，
  却仍要处理结构冒险（IF 与 MEM 抢存储器）——复杂度/收益比最差。
- 六级（IF1/IF2 + ID/EX/MEM/WB）：唯一动机是配合同步读（BRAM）指令存储器。本版选择零延迟
  读存储器，因此不需要；若未来需要 BRAM，迁移路径见 `03` §11（增补 IF2 级或 ready 握手）。

### 3.4 为什么五级 + 无分支预测
- 分支预测在本版被明确「不要求」。静态预测不跳转（predict-not-taken）不需要任何额外硬件，
  且与 EX 级解析天然配合。
- 分支/JAL/JALR 全部在 **EX 级**解析：此时两个操作数已经过前递网络就绪，无需为 ID 级再加
  一套前递/互锁。代价是每次「实际跳转」付出 2 拍冲刷；收益是**冒险逻辑只有一套**。
  在「性能第 6 位」的优先级下，这个交换是明确的。

---

## 4. 选定方案（一句话）

> **经典五级顺序单发射流水线（IF/ID/EX/MEM/WB），哈佛接口、零延迟组合读存储器、
> 静态预测不跳转、分支与跳转在 EX 级解析并冲刷 2 拍、EX/MEM 与 MEM/WB 双路前递、
> load-use 单拍互锁、无 Cache、无分支预测、无 CSR、无 M 扩展、fail-stop 精确陷阱。**

---

## 5. 被明确拒绝的机制（防止范围蔓延）

| 机制 | 拒绝理由 |
|---|---|
| I/D Cache | 明确不要求；单核裸机、无性能目标 |
| 动态分支预测（BHT/BTB/RAS） | 明确不要求；引入预测器状态与训练/恢复逻辑 |
| 乱序、多发射、寄存器重命名 | 明确不要求；验证状态空间爆炸 |
| CSR / 特权模式 / 陷阱向量 | RV32I 不要求；用 fail-stop 陷阱替代（`01` §5.1） |
| M/A/F/D/C 扩展 | 规格明令禁止 |
| 非对齐访存硬件支持 | 规范允许 trap；桶形移位器+跨字拼接属非必要复杂度 |
| 写直通/写回 Cache、总线协议（AXI/Wishbone） | 超出需求；接口保持「地址/数据/使能」最小形态 |
| 时钟门控、多电压域 | 功耗第 8 位，明确不做 |

---

## 6. 该方案下仍需实现的复杂度（诚实清单）

五级流水线相对单周期多出的**全部**机制，且每一项都有对应的验证手段：

| # | 机制 | 规模（估计） | 验证手段 |
|---|---|---|---|
| 1 | 前递网络（2 路 × 2 操作数 + 优先级） | ~40 行 | `tb_hazard.v` 真值表 + 随机差分 |
| 2 | load-use 互锁（1 拍停顿 + 气泡注入） | ~15 行 | 定向 load-use 程序 + 随机差分 |
| 3 | 分支/跳转冲刷（EX 解析 → 清 IF/ID、ID/EX） | ~25 行 | `programs/branch.S` / `jump.S` + 随机差分 |
| 4 | 流水线寄存器与 valid 位 | ~120 行 | 复位测试 + 差分状态比对 |

不存在其它「隐性」复杂度。

---

## 7. 结论

方案 D 在**正确性、可验证性、结构清晰度**三项最高优先级上均为最优或并列最优，代价是
~700 个触发器和三条有限状态的冒险规则；在「不追求性能」的约束下，它既保留了原始目标
（五级流水线），又没有引入任何规格之外的结构。选定方案 D，进入 Phase 3。

> 逃生舱（写给评审）：ISA 级验证环境（汇编程序 + 独立 ISS 差分 + 状态比对）**与微架构无关**。
> 若评审最终更偏好最简方案 B，只需替换 `rtl/core`，`tb/`、`tools/`、`programs/` 可原样复用。
